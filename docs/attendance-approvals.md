# 근태허가원 수집 연계 — 구현 계약

작성 2026-09-22. BRM(이 저장소)이 포털에서 직접 읽어 오는 방식의 계약이다.
이름·경로·필드를 바꾸려면 문서를 먼저 고친다.

## 1. 배경과 원칙

근태는 ERP 월 엑셀(`monthly_attendance_YYYY-MM.xlsx`)을 읽어 판정한다. 엑셀에 없는 정보는
추론으로 메운다(반차·반반차의 오전/오후). 결재 문서(근태허가원)에는 그 정보가 사실로 적혀
있으므로, 그것을 읽어 와 **보강 자료**로 쓴다.

원칙:

1. **판정의 근거는 계속 ERP 엑셀이다.** 허가원은 보강이며, 수집이 멈추면 BRM 은 종전대로 동작한다(fail-open).
2. **포털 수집은 BRM 이 직접 한다.** 자격증명도 BRM 운영 PC 의 환경변수에 둔다.
   - **이 항목은 2026-09-22 에 뒤집혔다.** 처음 계약은 "BRM 에 자격증명을 두지 않는다 ·
     별도 수집기가 결과만 밀어 넣는다"였다. 그 수집기가 **BRM 운영 서버와 다른 PC** 에서
     돌아 파일로도 HTTP 로도 넘길 길이 없었다(사용자 결정: 토큰을 새로 설정하지 않는다).
     그래서 수집을 BRM 안으로 들였다.
   - 브라우저 자동화는 여전히 넣지 않는다. 포털은 평범한 폼 로그인 + 서버 렌더 HTML 이라
     `requests` 만으로 읽힌다(2026-09-22 실측). 의존성을 새로 늘리지 않았다.
   - 자격증명은 **환경변수로만** 오고, 로그·감사 기록·화면 응답 어디에도 실리지 않는다.
     값이 없으면 기능이 꺼지고 책임자 화면이 "수집 설정 안 됨"이라고 알린다.
3. **공용 PC 배려**: 개인 사정(종류·사유)은 책임자 화면에서만 본다. 공용 화면·트레이는 "결재 있음"
   수준까지만(기존 [[feedback_tray_privacy]] 원칙과 동일).
4. 1단계는 **적재와 대조까지만**. 오전/오후 확정·이상 자동 해소는 2단계에서 따로 결정한다.

## 2. 수집 대상

- 문서함: **부서공개함**(`listApprDeptOpen`).
- 검색: **작성자(기안자) 비움** + **양식명**(`searchFormName`) `근태허가원`.
  기간은 완료일 기준 최근 N일(기본 60).
- **문서제목이 아니라 양식명으로 찾는다.** 실측(2026-09-23, 270일 같은 부서):

  | 검색 칸 | 잡히는 문서 |
  |---|---|
  | 문서제목 = `근태허가원` | **10건** |
  | 양식명 = `근태허가원` | 328건 |
  | 양식명 = `허가원` | 333건 |
  | 양식명 = `근태` | 344건 |

  제목으로 찾으면 344건 중 **334건을 놓친다**. 놓치던 것은 특별한 문서가 아니라 제목에
  '근태허가원'이라는 말이 안 들어간 평범한 휴가 결재다
  (`원료생산팀/26.09.21/정**/반반차`, `원료생산팀/김**/2026.09.23(반차)`). 제목으로 잡히던
  10건은 양식명으로 잡히는 328건의 부분집합이다.
  **양식명은 부분일치(LIKE)** 라 `근태` 한 낱말로도 걸린다.
  기본값은 `근태허가원`(`IRMS_PORTAL_FORM_NAME`) — 344건 중 328건을 덮고 정확히 우리 문서다.
  `근태` 로 넓히면 16건이 더 잡히지만 그것들은 본문 칸이 다른 별개 양식이라 '값 부족'으로만
  쌓인다. 넓히려면 운영자가 환경변수를 바꾼다.
- 창 크기별 실측 건수(양식명 `근태`): 30일 67 · 60일 96 · 90일 131 · 270일 344.
- **조회 범위를 회사 전체로 넓히지 않는다**(사용자 결정). `searchGroupId` 를 비워 보내면
  전사 조회가 되는데, 수집 계정이 실제로 읽을 수 있는 것은 자기 부서 문서뿐이다. 부서 기본값을
  그대로 둔다. 남의 부서 문서는 본문이 500 `접근 권한이 없습니다` 로 막히고, 그런 건은
  **건너뛰고 세기만 한다** — 제목만 보고 값을 지어내지 않는다.
- 문서 종류: 반반차 · 반차 · 연차 · 예비군 훈련 · 그 밖(원문 그대로 보관).
- 제목 형식은 사람마다 다르다. 양식명으로 찾기 시작하면서 **날짜 칸 안에 종류가 같이 적힌
  형식**(`원료생산팀/김**/2026.09.23(반차)`)이 다수가 됐다 — 날짜 칸을 통째로 건너뛰면
  그 문서가 전부 `기타` 로 접히므로, 날짜 칸 안에서도 종류 낱말을 찾는다.
- 목록 행에서 읽히는 값으로 우선 채우고, 부족하면 문서를 열어 본문에서 채운다.
- **실측(2026-09-22)**: 목록 칸은 문서번호·유형·분류·그룹사 여부·문서 제목·기안자·기안부서·완료일뿐이다.
  대상자·기간·오전/오후는 목록에 없어 **본문을 열어야** 한다. 본문의 `소속/사번/직위/성명`에서 대상자와
  사번을 얻고, `기간`의 시각으로 오전/오후를 가른다. **기안자와 대상자는 다를 수 있다**(팀장이 팀원 몫을 기안).
  결재상태 칸이 없어 `status` 는 사실상 늘 `완료`다. 부서공개함은 **수집 계정의 부서 문서만** 보인다.

## 3. 수집 규약 — BRM 이 포털을 직접 읽는다

구현: `src/services/portal_approvals/`(클라이언트 + 파서) · 적재는
`src/services/attendance_approvals.collect_from_portal`. 브라우저는 쓰지 않는다.

### 3.1 포털 호출 세 단계 (2026-09-22 실측)

1. **로그인** — 평문 폼 POST. 해시·RSA 없음.
   `GET  {base}/portal/main/portalMain.do` 로 `JSESSIONID` 를 받고,
   `POST {base}/login.do` 에 `j_username` · `j_password` · `j_gwIdCheck=""` 를 보낸다
   (헤더 `Referer` = 로그인 페이지, `Origin` = 호스트).
   성공 = portalMain 으로 302, 실패 = 200 인데 최종 URL 이 `/loginForm.do?error=1`.
   세션은 `JSESSIONID` 쿠키 하나뿐이고 CSRF 필드는 없다. 유휴 15분은 견딘다.
   세션이 끊기면 200 인데 본문에 `id="loginForm"` / `name="j_password"` 가 있다 —
   그것을 보면 다시 로그인하고 같은 요청을 **한 번만** 재시도한다.
2. **목록** — `POST {base}/approval/work/apprlist/listApprDeptOpen.do` (form-encoded).
   `listType=listApprDeptOpen` · **`searchApprTitle=`(빈 값)** · `searchUserName=` ·
   **`searchFormName=근태허가원`**(§2) · `searchStartDate=YYYY.MM.DD` · `searchEndDate=YYYY.MM.DD` ·
   `searchApprDocType=` · `searchIsGroupUse=` · `pageIndex=1` · `pagePerRecord=50` ·
   `sortColumn=apprEndDate` · `sortType=DESC` · `curRowIndex=0` · 빈 `apprId` ·
   `linkType` · `entrustUserId` · `apprIds`. **`searchGroupId` 는 보내지 않는다**(§2).
   응답은 서버 렌더 HTML 이고 행은 `<table id="listTable">` 안의 `<tr>` 다. 각 행의
   `onclick="getApprDetail('<apprId>',…)"` 에 본문 조회 키가 있다(문서번호와 다르다).
   **날짜 필터는 완료일 기준**이다. 쪽 넘김은 `pageIndex` 를 올리는데, 끝을 넘으면
   마지막 쪽으로 붙들리므로 **새 apprId 가 하나도 없으면 멈춘다**. 같은 문서가 여러 행으로
   나올 수 있어 **문서번호로 합친다**.
3. **본문** — `GET {base}/approval/work/apprWorkDoc/viewApprDoc.do?apprId=…&listType=listApprDeptOpen`.
   iframe 없음. 응답에 HTML 이스케이프된 JSON 두 덩이가 들어 있다 —
   서식 `{"type":"text","name":"text6",…,"title":"기간"}` 과
   값 `{"type":"text","name":"text6","value":"26년08월07일 13시부터 ~ …"}`.
   `html.unescape` 후 `name` 으로 맞물려 라벨→값을 만든다(소속 · 사번 · 직위 · 성명 ·
   기간 · 사유 · 행선지 · 긴급연락처). 문서번호 · 기안일자 · 기안자는 머리글 글자에 있다.
   **다른 부서 문서는 500 `접근 권한이 없습니다`** — 포털 권한이지 전송 문제가 아니다.

### 3.2 언제 도는가

- **'지금 가져오기' 버튼** — 책임자 근태 화면의 '결재 대조' 구역.
  `POST /api/attendance/admin/approvals/collect` (책임자 전용). 누르는 동안 버튼이 잠기고
  지난 시간을 세어 보여준다(첫 회차는 분 단위로 걸린다).
- **하루 1회 자동** — `serve.py` 의 일일 슬롯이 `tools/collect_attendance_approvals.py --daily`
  를 부른다(일일 백업·취소 기록 정리와 같은 자리). 앱 lifespan 에 배경 태스크를 두지 않은
  이유는 그 파일 상단 주석에 있다. `--daily` 는 오늘 **끝낸** 회차가 있으면 건너뛰고,
  겹친 실행은 DB 잠금(10분 만료)이 막는다.
- 책임자가 화면을 **여는 것만으로는 포털을 부르지 않는다**(읽기 전용 조회).

### 3.2-1 이미 가진 문서는 다시 열지 않는다

한 회차의 비용은 사실상 **본문 왕복**이 전부다(문서 하나가 0.3~0.5초). 기본 창 60일이
실측 96건이라, 매번 전부 열면 두 번째 회차부터는 통째로 헛수고다.

- 목록 행(문서번호 · 제목 · 기안자 · 기안부서 · 완료일)으로 **지문**을 만든다. 이 값이
  저장된 `doc_hash` 와 같으면 본문을 열지 않고 `그대로`로 센다.
- 결재가 다시 완료되면 완료일이 바뀌어 지문도 바뀐다 → 그 문서만 다시 연다.
- **열어 봤지만 저장할 수 없던 문서**(권한 없음 · 필수 값 부족)는 표에 남지 않아 위
  지문으로는 걸러지지 않는다. 그래서 그 지문을 따로 기억한다(`app_settings`). 이 기억이
  없으면 그런 문서가 회차마다 다시 열려 상한을 먹고, **밀린 문서가 영영 안 들어온다**
  (2026-09-23 실연에서 실제로 막혔다 — 몇 번을 눌러도 남은 수가 줄지 않았다).
  건너뛰어도 '읽을 수 없음 N · 값 부족 N' 건수는 그대로 알린다.
- 그래서 **첫 회차만 느리고 이후는 몇 초**다.

### 3.2-2 한 회차 상한

- 한 회차에 **새로 열 본문은 120건까지**(`collector.MAX_BODIES`). 이미 저장된 문서는
  세지 않는다. 목록은 20쪽까지 읽는다(실측 270일이 7쪽).
- 상한에 걸리면 못 연 수를 `remaining` 으로 돌려주고, 화면이 "아직 N건 남음 · 다시 누르면
  이어서 가져옵니다"로 적는다. **최신 문서부터** 열기 때문에 회차가 나뉘어도 오늘 것이 먼저
  들어온다.
- 자동 실행도 같은 상한을 쓴다. 남은 문서가 있으면 `--daily` 가 그날 다시 돌 수 있게
  건너뛰지 않는다(다음 슬롯에서 이어 받는다).

### 3.3 저장 항목 하나의 모양

```json
{
  "doc_no": "20260805P227-0040",
  "emp_name": "박용재",
  "emp_id": "171013",
  "kind": "반차",
  "half": "오후",
  "start_date": "2026-08-07",
  "end_date": "2026-08-07",
  "status": "완료",
  "drafted_at": "2026-08-05",
  "title_raw": "근태허가원/원료생산팀/박용재/반차/26.08.07",
  "doc_hash": "sha256:…"
}
```

- 필수: `doc_no` · `emp_name` · `kind` · `start_date`(`YYYY-MM-DD`). 하나라도 못 읽으면
  **저장하지 않고 화면에 '값 부족'으로 보고한다** — 추측해서 채우지 않는다.
- `end_date` 가 없으면 `start_date` 와 같게 채운다.
- `half` 는 글에 '오전/오후'가 적혀 있으면 그대로, 없으면 **기간의 시작 시각**으로 가른다
  (13시부터 → 오후). 연차·예비군 같은 하루 단위 종류에는 적용하지 않는다.
- `kind` 는 원문 그대로 저장하고(`kind_raw`) 정규화는 BRM 이 한다(표는 §4).
- `doc_hash` 는 목록 행 값(문서번호·제목·기안자·부서·완료일) + 파서 판 번호로 만든다.
  결재가 다시 완료되면 완료일이 바뀌어 해시가 바뀌고 그때 다시 저장된다. 해석 규칙을 고치면
  `PARSER_VERSION` 을 올려 이미 적재된 문서도 다시 읽히게 한다.
- 적재는 `doc_no` upsert 뿐이다. **창에서 빠진 문서를 지우지 않는다.**

### 3.4 운영 PC 환경변수

| 변수 | 뜻 |
|---|---|
| `IRMS_PORTAL_USERNAME` | 포털 아이디. 없으면 기능 꺼짐 |
| `IRMS_PORTAL_PASSWORD` | 포털 비밀번호. 없으면 기능 꺼짐(앞뒤 공백 보존) |
| `IRMS_PORTAL_BASE_URL` | 기본 `https://portal.interojo.com` |
| `IRMS_PORTAL_FORM_NAME` | **양식명** 부분일치 검색어. 기본 `근태허가원`. 넓히려면 `근태`(§2 표) |
| `IRMS_PORTAL_WINDOW_DAYS` | 완료일 기준 조회 창(일). 기본 60(실측 96건) |
| `IRMS_PORTAL_TIMEOUT_SEC` | 요청 하나의 제한시간(초). 기본 20 |

`.env` 에 적는다. 저장소에는 넣지 않는다.

## 4. BRM 저장·해석

표 `attendance_approvals`:

| 열 | 뜻 |
|---|---|
| `doc_no` TEXT UNIQUE | 결재 문서번호. 멱등 키 |
| `emp_name` TEXT NOT NULL | 대상자 이름(원문) |
| `emp_id` TEXT | 사번. 없으면 null |
| `kind_raw` TEXT NOT NULL | 문서의 종류 문자열 원문 |
| `kind` TEXT NOT NULL | 정규화: `연차` `반차` `반반차` `예비군` `기타`. 포털 종류 칸의 `훈련` 은 `예비군` 으로 접는다 |
| `half` TEXT | `오전` `오후` null |
| `start_date` / `end_date` TEXT | `YYYY-MM-DD`. end 없으면 start 와 같게 |
| `status` TEXT | 결재 상태 원문 |
| `drafted_at` TEXT | 기안일 |
| `title_raw` TEXT | 목록 제목 원문(사람이 대조할 근거) |
| `doc_hash` TEXT | 수정본 감지 |
| `source` TEXT NOT NULL | `portal` |
| `collected_at` / `updated_at` TEXT | 수집·갱신 시각 |

- 인덱스: `(start_date)`, `(emp_name, start_date)`.
- 사람 맞추기: `emp_id` 가 있으면 그것으로, 없으면 **이름 + 그 달 ERP 명단**으로 맞춘다.
  동명이인이면 맞추지 않고 `미매칭`으로 남긴다 — 조용히 아무나에게 붙이지 않는다.

## 5. 책임자 화면(1단계)

근태 책임자 월 화면에 '결재 대조' 구역을 둔다.

1. 그 달 허가원 목록: 날짜 · 이름 · 종류 · 오전/오후 · 상태 · 문서번호.
2. 대조 결과 두 갈래:
   - 허가원은 있는데 ERP 엑셀에 휴가 표시가 없는 건.
   - ERP 엑셀에 휴가가 있는데 허가원이 없는 건.
3. 미매칭(사람을 못 맞춘 건) 목록.
4. 수집 상태 한 줄: 마지막 수집 시각과 건수. 오래되면(2일) 눈에 띄게 알린다.
   설정이 없으면 "수집 설정 안 됨".
5. '지금 가져오기' 버튼(책임자 전용). 누르는 동안 잠기고, 끝나면 결과 한 줄을 알린다.
6. 지난 회차에 못 읽은 것이 있으면 그 한 줄과 목록(문서번호 · 사유):
   권한이 없어 건너뛴 건 · 필수 항목을 못 읽어 저장하지 않은 건 · 적재가 거절한 건.

판정·알림·트레이는 1단계에서 **바꾸지 않는다**.

## 6. 검증

- 적재: 멱등(같은 배치 두 번 = 갱신 0), 수정본 갱신, 필수 누락 거절 목록,
  대조 세 목록의 계산, 동명이인 미매칭.
- 수집: 실제 포털을 부르지 않고 세 단계(로그인·목록·본문)를 가짜 응답으로 덮는다 —
  로그인 실패, 유휴 만료 후 재로그인, 쪽 넘김이 마지막 쪽으로 붙드는 경우, 같은 문서번호
  중복, 본문 500(권한 없음), 제목을 못 읽는 문서, 자격증명 미설정.
- 검색 칸: 양식명을 보내고 문서제목은 비우는지, 기본값·환경변수 덮어쓰기.
- 다시 열지 않기: 저장된 문서는 본문을 안 열고, 완료일이 바뀐 문서만 다시 여는지.
- 상한: 걸리면 남은 수를 알리고, 다시 부르면 이어 받는지.
- 기간에 시각이 없는 문서는 오전/오후를 지어내지 않고 `half` 를 비워 저장하는지.
- 실패해도 저장된 행이 그대로인지(로그인 실패·예외 모두).
- 개인정보: 공용 화면·트레이 응답에 종류·사유가 실리지 않는지, **자격증명이 응답·감사·
  로그 어디에도 없는지** 확인.
